# 연결·설정 복구 구현안

요청: 연결·설정의 세부 동작을 테스트하고 실제 사용할 수 있도록 분석·설계한다. [현재 검증 결과](../verification/2026-11-17-settings-audit.md), [기존 #8 계약](../tasks/8-connection-settings.md)을 기준으로 한다. 이번 산출물은 설계이며 제품 코드는 변경하지 않았다.

## 방향

기존 연결 클라이언트와 API를 유지하고 실행 시 진단과 조회 복구를 보완한다. 현재 화면은 설정 저장기가 아니다. 비밀정보는 기존 Infisical 관리 경로에 두고 브라우저에는 상태·복구 안내만 제공한다.

예를 들어 현재처럼 4개 값이 없으면 첫 단계에서 중단 원인과 재시작 방법을 보여준다. 주입된 서버가 시작된 뒤 인증 응답을 받으면 두 번째 단계만 성공한다. 잔고 전 페이지가 끝나야 세 번째 단계가 성공한다. 상태 새로고침은 서버의 마지막 관측만 읽는다.

| 대안 | 변경 비용 | 현재 문제 해결 | 비밀정보 경계 | 결정 |
| --- | --- | --- | --- | --- |
| 기존 CLI 주입 + 진단/복구 보강 | 낮음 | 미주입 식별·조회 대기 해결 | 기존 서버 전용 유지 | 채택 |
| 웹 비밀값 편집 + Infisical 관리 API | 높음 | 웹 설정 편집까지 가능 | 추가 인증·권한·감사 필요 | 현재 범위에서 보류 |

주입을 웹에서 직접 편집해야 한다는 요구가 확정되면 두 번째 대안을 별도 설계한다. 현재 증거만으로 새 설정 DB·인증 클라이언트·프로필 시스템을 만들 필요는 없다.

## 구현 순서와 완료 조건

### 1. 실행 환경 진단

F1/F4 때문에 첫 순서는 운영 경로 확인이다. 실제 사용 경로와 포트의 서버를 식별하고, 기존 Infisical 프로젝트·dev /kis 연결을 확인한다. 안전한 인증 절차 후 승인된 시점에 주입 실행·재시작한다. 단순 상태 새로고침을 재주입처럼 안내하지 않는다.

- `server/http.ts`: 기존 instanceId에 비밀이 아닌 startedAt 추가. 작업 디렉터리 전체 경로나 환경변수 원문은 노출하지 않는다.
- `shared/model.ts`, `shared/contracts.ts`: 서버 식별 계약을 함께 확장한다.
- `src/pages/Operations.tsx`: 서버 시작 시각·짧은 인스턴스 ID, 필수 값 상태, 다음 행동을 표시한다. 첫 단계 명칭은 “서버 필수 설정”으로 명확히 한다. Infisical 출처 확인과 구분한다.
- `scripts/dev.ts`: 필요 시 별도 KIS 실행 모드만 주입 사전검사를 적용한다. 기본 DEMO 실행은 유지한다. 이미 점유된 포트에서는 기존 프로세스를 종료하지 않고 안전한 오류로 중단한다.
- 완료: 누락/형식오류/주입됨이 분리되고, 재시작 후 인스턴스 변경을 확인한다. 환경변수 존재만으로 인증 성공을 표시하지 않는다.

### 2. 조회 시간 제한과 복구

F2 때문에 연결 확인에만 유한한 시간을 적용한다. 공통 act 전체에 같은 제한을 적용하면 주문의 응답 불명 처리까지 바뀔 수 있으므로 범위를 제한한다.

- `server/kis.ts`: 기존 요청 간격·토큰 공유·잔고 요청 합류를 유지한다. 잔고 조회 한 작업에 전체 deadline을 둔다. 설계 초깃값은 120초이며 관측 후 조정한다. 기존 `limitRequestsFor()`는 클라이언트 전체에 지속 적용되므로 화면 조회에서 재사용하지 않는다.
- deadline은 큐 대기·토큰 발급·응답 본문·연속 페이지를 포함한다. 만료 후 다음 페이지를 보내지 않고 partial/error로 종료한다. 마지막 전체 성공 잔고는 보존한다.
- `src/App.tsx`: kis/check에만 서버 한도보다 긴 클라이언트 제한(초안 125초)을 적용한다. timeout은 성공/실패 확정 대신 “응답 확인 지연”으로 표시하고 GET 상태 재조회를 허용한다. 브라우저 대기 중단이 서버 취소를 보장하지 않음을 유지한다.
- `src/pages/Operations.tsx`: GET 상태 새로고침을 check의 busy와 분리한다. 실행 중 동일 check는 잠그고 새로고침만 허용한다. 자동 POST 재전송은 하지 않는다.
- 완료: 영구 미응답·다중 페이지 지연에서도 유한 시간 안에 복구 동작이 열리고, 부분 잔고를 새 성공으로 표시하지 않는다. 주문 POST와 승인 원장은 기존 동작을 유지한다.

### 3. 재시도·진행 표시

F3 때문에 기존 retryAt을 UI 제어에도 사용한다. 남은 대기 시간을 표시하고 그동안 연결 재시도를 막는다. 시간이 지나면 수동 재시도를 허용한다. 잔고 조회 중에는 경과 시간·페이지 수를 표시한다. 상태 새로고침에는 “외부 KIS 호출 없음”을 덧붙인다.

완료: 60초 대기 fixture에서 초 단위 표시와 버튼 복구를 확인한다. 서버 시간 차이·잘못된 시각은 계약 검증으로 처리한다. 다른 화면의 상태 확인은 막지 않는다.

## 검증과 인수

| 단계 | 추가 검증 | 통과 기준 |
| --- | --- | --- |
| 단위·HTTP | 전체 deadline, 큐 대기, 중복 조회 합류, 상태 응답 필드 | 제한 후 후속 호출0, 이전 잔고 보존, 값 비노출 |
| 브라우저 | 응답 보류, GET 실패/복구, cooldown, 재시작, 60초 잔고 stale | 무한 버튼 잠김 없음, 오성공 없음, 재시도 가능 |
| 회귀 | 기존 KIS·HTTP·설정 E2E, typecheck/build | 기존 35+12건 유지, 새 재현 검사 통과 |
| 실제 연결 | 허용 시 Infisical 주입 → 모의 인증 → 전체 잔고 조회 | 시각·단계·페이지·오류 종류만 기록, 주문 없음 |

실제 연결 검증은 현재 STATE의 API 실행 제한이 해제된 범위에서만 수행한다. 이번 테스트 PASS는 실제 인증·잔고 조회 성공을 뜻하지 않는다. 구현 착수 시 최신 코드·관련 이슈 상태를 다시 고정하고, 다중 파일 변경 완료 경계에서 프로젝트 외부 리뷰 절차를 적용한다.

## 출처와 제한

- 로컬 근거: `src/App.tsx:35` 상태 조회, `src/App.tsx:65` 공통 액션, `src/pages/Operations.tsx:88` Settings, `server/kis.ts:233` 연결/잔고, `shared/status.ts` 신선도.
- [KIS 공식 샘플](https://github.com/koreainvestment/open-trading-api)은 인증·모의/실전 샘플 탐색의 공식 출발점이다. 실제 API 계약의 전체 필드를 이번 설계에서 새로 검증하지 않았다.
- [Infisical CLI 공식 참조](https://infisical.com/docs/cli/reference)에서 secrets-manager/run 항목을 확인했다. 상세 run 페이지는 도구 접근 실패로 읽지 못했다. 주입 명령은 기존 프로젝트 INFISICAL.md의 검증된 경로를 사용하며 이번에 실행하지 않았다.
- 120/125초, 필드 추가, 버튼 분리는 본 설계의 제안이다. 외부 서비스의 보장 수치가 아니다.
