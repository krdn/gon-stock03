# #98 KIS 모의 연속전략 계약

[#25 초안](25-validation.md#연속전략-별도-계약-초안--2026-11-18)을 저장 KIS 전략의 서버 전송 경로에 적용한다. 실행 계약·계좌 정보·실행 일시는 저장소에 제공하지 않는다.

## 계약 입력과 시작

서버 시작 시 운영자가 별도로 승인한 내용을 `KIS_STRATEGY_CONTRACT` JSON으로 전달한다. 모든 필드는 필수다. 전용 DB에 KIS 전략을 미리 저장하고, 전략 ID와 설정이 일치하는지 확인한다. 계약 등록만으로 전략이 시작되지 않는다. 현재 실시간 구독, 신선한 시세와 REST 대조 완료 후 개별 시작이 필요하다.

| 필드 | 집행 기준 |
|---|---|
| contractId, ledgerPath, accountFingerprint | UUID, 명시한 STOCK_DB의 실제 절대 경로, 서버의 모의 계좌 8자리와 상품 2자리를 콜론으로 연결한 문자열의 SHA-256 소문자 hex. 파일명은 strategy-{contractId}.sqlite. 실제 값은 비공개로 관리 |
| strategyId, revision, code, fast, slow, qty | 저장 전략 ID·revision·6자리 종목·단기/장기 기간·주문 수량과 정확히 일치해야 함 |
| startsAt, endsAt | UTC 또는 오프셋 포함 ISO 일시. UTC로 정규화하며 시작 포함·종료 제외. 기존 장운영·실시간 시세 검사를 함께 적용 |
| maxOrderAmount, maxAttempts, maxTotalAmount | 양의 안전 정수. 지정가×고정 수량의 주문당 원화 한도, 총 예약 시도 수, 매수·매도 합산 누적 주문대금 한도 |
| sellPolicy | deny는 매도 차단. account는 기존 수동 보유도 포함하며 고정 수량 전부가 보유량−미체결 매도와 조회된 주문가능수량 이내여야 함. 주문가능수량 누락 시 차단. 전략 취득분만 구분해 매도하는 정책은 미지원 |

## 상태 전이와 실패 처리

1. 고정된 계약이 있는 DB는 계약 누락·내용 변경·다른 계좌·#75 고정 1회 승인과 혼용하면 시작을 거부한다. 같은 DB와 계약으로 재시작하면 누적 사용량을 유지하고 전략은 정지한다. 계약 모드의 수동 신규주문과 시장가는 거부한다. 계약 없는 일반 앱의 수동 주문과 DEMO는 기존 동작을 유지한다.
2. 시세 이벤트 키는 거래일과 누적 거래량으로 정한다. 같은 계약의 같은 이벤트에는 한 번만 예약할 수 있다. 공통 대조와 위험 검사 후 SQLite 쓰기 트랜잭션에서 계약·실행 상태를 다시 확인한다. 예약 행, sending 주문, 감사 기록을 함께 커밋한다. 이 때부터 거절·응답 불명·부분체결·만료·프로세스 종료에도 한도는 반환하지 않는다. 커밋 전 실패는 전부 롤백한다.
3. 모의 지정가 POST 직전 시간·신호·정지·위험을 다시 검사하고, 저장된 sending 주문과 내용이 같은 미사용 예약만 한 번 소비한다. POST 자동 재전송은 없다. 응답 불명은 원장 대조가 필요하다. 누적 한도 소진·응답 불명·기간 만료 뒤에는 새 전송을 차단한다. 단절·프로세스 재시작 후 대조만으로 전략을 재개하지 않는다.
4. `GET /api/kis/ledger`의 `strategyBudget`에 attempts, amount, maxAttempts, maxTotalAmount를 제공한다. amount는 예약 주문대금 합계다. 체결대금과 수수료는 별도로 대조한다.

내구성은 승인된 같은 원장을 보존하는 조건이다. 이전 백업 복원·원장 교체·시계 변경을 독립 탐지하는 외부 감사 서비스는 이번 범위 밖이다. 저장된 권한이나 원장을 재설정해 #75 승인을 재사용하지 않는다. 현재 새 거래 승인은 없다.

## 검증 기록

격리 단위/API 223개와 브라우저 150개 통과. 빌드 성공, 기존 번들 크기 경고 유지. 두 독립 worker가 마지막 한도를 두고 경합할 때 정확히 한 건만 예약됐다. 요청·이벤트 중복, 감사 저장 실패 롤백, 전송 직전 만료, 부분체결 후 최초 금액 보존, 응답 불명과 재시작을 검증했다. 임시 DB·가짜 계좌로 실제 서버 진입점에서 기동을 확인했고 같은 원장에서 계약 제거·한도 변경·계좌 지문 불일치의 세 재시작을 모두 거부했다. 브라우저 검사 첫 실행은 임시 사본에 dist가 없어 준비 시간이 만료됐고 빌드 후 통과했다.

Argon 설계 검토는 영구 원장 고정·비복원 예약·전송 직전 대조와 계좌 보유 매도 조건을 확인하도록 지적했다. 전체 코드 검토는 최종 이벤트 상태 ERROR와 함께 P0/P1 없음·P2 세 건을 반환했다. 예약 직전 실시간 상태 재검사, 기존 전략 요청 ID를 사용한 수동 주문 거부, REST 조회 전 잔여한도 검사로 반영했다. 실증 계좌의 주문·취소·전략 전송은 0회다.
