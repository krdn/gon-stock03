# #9 최소 모의 실행 절차

**실제 조회 후 주문전 guard 중단.** [실행 결과](../verification/2026-11-16-paper-session-run.md)를 확인한다. [2026-11-16 승인 기록](https://github.com/krdn/gon-stock03/issues/9#issuecomment-6897995215)에서 사용자는 아래 범위에 “수동 취소 대안에 동의”, “조건부 모의 주문 1회 승인”으로 각각 응답했다. 이 최초 기록은 준비 승인이다. 이후 사용자가 직접 API 주문·취소 테스트와 정규장 전체 시간창 확대를 지시했고, 동일 모의계좌·다른 API 중지·앱 잔량취소 대응 가능을 확인했다. 실제 전송은 아래 준비 검증과 장 상태·최신 데이터 확인 후 수행한다. 예약은 하지 않는다. [공식 계약·대안](../research/kis-order-recovery-2026-11.md)과 [검증](../verification/2026-11-15-kis-orders-recovery.md)을 먼저 확인한다.

## 실행 전후 절차

1. #9의 2026-11-16 사용자 승인 기록과 위 범위를 대조한다. 같은 범위의 승인을 다시 요청하지 않는다. 범위 변경은 별도로 결정한다.
2. 아래 원장·서버 절차로 승인 대상 커밋, 백업, 단일 서버를 확인한다. `.codex/config.toml`은 보존한다.
3. [Infisical 지침](../INFISICAL.md)으로 주입한다. 키·계좌번호·토큰·응답 원문을 로그나 PR에 저장하지 않는다.
4. API 모의 계좌와 공식 앱 계좌가 같고 앱에서 잔량 취소가 가능한지 사용자가 확인한다. 확인 불가면 주문하지 않는다.
5. 잔고·전체 주문을 조회한다. 미확정 주문, 기존 미체결, 대상 종목 보유, 위험 정지·손실 한도, 연결 오류가 있으면 중단한다. 위험 설정을 자동 완화하지 않는다.
6. 서버 설정에 고정한 UUID 1개와 정확한 단가를 지정해 기존 `POST /api/kis/order`를 한 번 호출한다. 서비스가 `sending`을 원장에 먼저 저장한 뒤 전송한다. 원장에 주문을 수동 선삽입하지 않는다. 실제 전송 시각도 실행 창 안이어야 한다.
7. 제한 모드가 성공·거부·불명·사전검사 실패 후 신규 주문을 정지한다. 이를 확인하고 REST 조회만 진행한다. 접수번호와 거래일·조직·종목·방향·수량·가격을 대조한다. 네트워크·계약·수량 불일치면 자동 재전송 없이 중단한다.
8. 잔량 처리는 위 최대1회 API 취소 후보와 앱 취소 대안에 따른다. 체결·취소 ACK만으로 완료를 선언하지 않는다. 미관측 취소·부분체결·경합은 #25 V01에 별도로 남긴다.
9. 민감값을 제거한 접수/대조 시각·상태·체결/잔량·대상 SHA·감사 ID와 사용자 관측을 #9에 기록한다. 사용자 육안 수용과 fixture 결과를 구분한다.

조회에 없는 번호 없는 불명은 자동 해제하지 않는다. 명시적 복구를 하려면 원래 계좌·주문 근거를 확인하고 inspect→confirm 절차를 별도로 수행한다. 이 1건 실행 승인은 임의의 기존 불명 해제 승인까지 포함하지 않는다.

## 승인과 남은 실행 조건

- 사용자는 웹 취소를 보류하고 **공식 모의 앱 수동 취소 + REST 대조**로 최소 실증하는 대안에 동의했다. 웹 취소의 409 차단을 해제하거나 지원 완료로 표시하지 않는다.
- 사용자는 위 1주·100,000원 상한·주문 POST 1회·시간창·정지 조건을 승인했다. 미체결·거부·불명이어도 주문 재전송, 매도, 정정, 반복 전략은 승인하지 않았다.
- 2026-11-16 직접 테스트 지시와 동일 API/앱 모의계좌·타 API 중지·앱 잔량취소 가능 확인을 받았다. 사용자는 공식 앱의 현재069500 장중·모의 주문 가능 상태도 확인했다. 최신 시세·잔고·원장과 코드/리뷰/CI·백업 검증을 마친 뒤 정규장 안에서 실행한다.
- 준비 검증이 끝나면 승인된 실제 모의 테스트를 즉시 진행하되 예약·상주 대기는 하지 않는다. 결과를 얻기 전 성공으로 표시하지 않으며 #9 OPEN/Blocked와 후속 차단을 유지한다.

## 실행 당일 원장·서버 준비

아래는 **사용자의 직접 실행 지시 후** 적용할 작업 명세다. 실제 수행 여부는 실행 기록을 따른다.

1. 실행할 PR의 고정 SHA와 최종 CI를 확인한다. 다른 API 서버·CLI·수집기와 웹 탭의 자동 조회를 종료했는지 확인한다. 4303/4304 포트와 프로젝트 서버 프로세스가 비어 있어야 한다. `flock`만으로 기존 비협력 프로세스가 정지됐다고 판단하지 않는다.
2. 원장 출처 후보는 `/home/gon/llm-projects/gon-stock03/.local/workspace.sqlite`다. 현재 존재만 확인했으며 실제 원장 내용·계좌 연속성은 읽지 않았다. 사용자가 사용한 최신 모의 원장이 맞는지 확인한다. 맞지 않거나 출처가 모호하면 중단한다.
3. 서버가 모두 종료된 상태에서 Python `sqlite3`의 읽기 전용 URI(`mode=ro`) 연결과 `Connection.backup()`으로 WAL을 포함한 일관된 백업을 만든다. 원본은 수정하지 않는다. 원장 열람에 `Store` 생성자를 사용하면 재시작 기록을 쓰므로 사용하지 않는다.
4. 준비 폴더의 `.local/backups/<확인일>-before.sqlite`에 백업한다. 새 파일에만 저장하고 `PRAGMA quick_check = ok`, 원장·감사 건수 일치, SHA-256과 권한0600을 확인한다. 내용·계좌정보는 출력하지 않는다.
5. 검증한 백업에서 `.local/kis-minimum-paper.sqlite`를 만든다. 이번 실행부터 이 절대경로만 원장으로 사용한다. 기존 원장은 보존한 이전 사본으로 취급하며 재가동하지 않는다. 기존 실행 사본이 있으면 덮어쓰지 않고 소비 기록·SHA부터 확인한다. 실행 후 원장과 감사의 새 백업도 같은 전용 폴더에 보관한다.
6. 실행일과 UUID를 비밀값 없는 로컬 실행 기록에 고정한다. `KIS_PAPER_APPROVAL='{"date":"확인한 YYYY-MM-DD","requestId":"고정 UUID"}'`, `STOCK_DB=전용원장의절대경로`, `STOCK_PORT=4304`를 프로세스 환경으로 설정한다. `.env`, `.codex`, 원본 폴더는 편집하지 않는다. 이 JSON은 형식 예이며 그대로 실행할 수 없다.
7. 사용자 인증이 유효한 Infisical `dev /kis` 주입으로 `flock -n /tmp/gon-stock03-kis-paper.lock infisical secrets-manager run --env dev --path /kis -- npm start`를 전용 cwd에서 전경 실행한다. watch·개발 서버·재시작 관리자·두 번째 서버는 사용하지 않는다. 주입 실패면 기존 서버 유무부터 확인하고 중단한다.
8. 네트워크 없는 `GET /api/kis/ledger`의 `minimumRun.active=true`, 날짜·ID와 로컬 기록을 대조한다. `/api/state`에서 정지·위험 한도를 확인한다. 이미 정지됐으면 자동 해제하지 않는다. 서버 기동과 설정 일치 자체는 계좌 인증·조회 성공이 아니다.

## 수동 시작과 대조

사용자에게 필요한 문장은 다음 사실을 포함한다. **승인을 다시 묻는 문장이 아니다.**

> 실행일은 YYYY-MM-DD다. API와 공식 모의 앱의 계좌가 같고, 해당 앱에서 잔량 수동 취소가 가능함을 확인했다. 다른 API 운용은 없으며 잔량을 직접 취소할 수 있다. 기존 조건대로 지금 수동 시작한다.

이 지시는 지정일 09:00–15:30 KST에 받아야 한다. 에이전트는 그때 공식 개장/특별 공지, 앱 장 상태와 마스터 종목을 확인한다. 확인이 실패하거나 시간이 부족하면 주문하지 않는다. 과거 승인이나 날짜 선택만으로 자동 시작하지 않는다.

- 최신 전체 잔고·주문은 `POST /api/kis/orders`로 확인한다. 시세는 마스터에 등록된 069500의 `POST /api/market/quote`로 얻는다. 요청 헤더는 `Content-Type: application/json`, `X-Workbench: local`이다. 인증·조회는 이때만 수행한다.
- 사전조건이 모두 맞으면 `/api/kis/order`에 `{code:"069500",side:"buy",qty:1,price:확인한현재가,requestId:고정UUID}`를 딱 한 번 전송한다. HTTP 클라이언트 재시도 옵션·루프·재클릭은 사용하지 않는다. 내부 재조회 중 가격이 달라지면 중단하며 가격을 바꾸어 다시 보내지 않는다.
- 응답 후 `/api/state`의 `risk.halted=true`를 확인한다. 서버가 응답하지 않으면 다시 주문하지 않고 서버 프로세스를 종료한 뒤 원장을 보존한다. `sending`은 다음 기동 때 `unknown`이 된다.
- 응답 직후 `/api/kis/orders`를 대조한다. 잔량이 확인되면 `cancelProbe:true`인 실행에서 `/api/kis/cancel-probe`를 최대1회 호출하고 REST로 최종 상태를 대조한다. 거부·불명 또는 약30초 시점 잔량은 사용자에게 앱 수동 취소를 요청한다. 필요하면 약60·90·110초에 조회한다. 하나의 요청이 끝나기 전에 다음 조회를 겹치지 않는다. 최종 체결/취소가 확인되면 일찍 종료한다.
- 조회 실패·수량 모순·번호 불일치는 즉시 자동 조회를 멈춘다. 120초 만료는 진행 중 응답도 중단한다. 이후 서버를 종료하고 마지막 상태·불명 여부를 기록한다. 재시작해서 조회 시간을 연장하지 않는다. 사용자 앱의 잔량 처리 확인이 늦으면 별도 증거로 남긴다.
- 원장·감사 원문은 로컬0600 보관만 한다. #9에는 SHA, 승인 댓글, 수신/대조 시각, 감사 ID, 상태, 수량·잔량과 사용자 관측만 요약한다. 계좌번호·키·토큰·전체 잔고·응답 원문을 게시하지 않는다.

동일 계좌·취소 가능·현재 앱 장 상태의 사용자 확인과 실제 최신 데이터 조회 결과는 구분한다. 준비 fixture PASS는 실제 접수/체결 증거가 아니며 #9 및 후속9개 차단을 유지한다.
