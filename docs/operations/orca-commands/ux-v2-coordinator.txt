krdn/gon-stock03의 2차 UI/UX 업그레이드를 총괄하는 Codex 메인 세션으로 작업하라. 한국어로 진행한다.

목표
사용자가 각 화면에서 “무엇을 할 수 있는지, 어떤 데이터를 보고 있는지, 버튼을 누르면 무엇이 바뀌는지” 이해하고 수정 지점을 가리킬 수 있게 하라. ‘지난 KIS 실행 기록’의 실측 → Gemini Neon과 판단 → 구현 → 실제 웹 재검증 방식을 나머지 화면에 적용한다.

시작과 재개
1. 현재 Orca 프로젝트 ID·worktree 경로·Git origin을 확인한다. 대상은 krdn/gon-stock03이다. 기본 checkout /home/gon/llm-projects/gon-stock03은 main·4303의 대조 기준이고, 구현은 배정된 worktree에서 한다. 다른 프로젝트면 여기서 멈춘다.
2. AGENTS.md, docs/STATE.md, docs/WORKFLOW.md와 선택 작업의 필수 자료를 읽는다. GitHub Project #25(https://github.com/users/krdn/projects/25), 상위 이슈 #149, 통합 PR #187, 기록 PR #153, 지도 #143·PR #144, 연결된 페이지 이슈·PR·CI의 최신 상태를 대조하라. 주문 화면 기준 사례는 docs/tasks/147-orders-ux.md와 병합된 PR #146·#148이다.
3. GitHub 담당 기록과 Orca의 실제 coordinator·Run·Task·dispatch·worktree를 함께 확인한다. 다른 활성 메인이 있으면 그 위치와 다음 행동만 보고한다. 소유권 또는 조회 결과가 불분명하면 해당 작업은 읽기 전용으로 확인하고 중복 배정하지 않는다. 인계가 확인된 경우 기존 Run·작업 기록을 이어간다.
4. 페이지마다 ‘진행 중 / 검토·승인 대기 / 완료 / 미배정’을 판단한다. 기존 작업자·PR은 재사용하고 승인 대기 항목은 유지한다. 모든 항목이 검토·병합·수용 대기 또는 완료라면 현재 화면·PR 링크와 결정할 사항만 보고하고 기다린다. 확인된 미배정 항목 중 승인 범위에 속하고 의존성이 풀린 작업만 새로 배정한다.

범위와 배정
- src/App.tsx, src/specs.ts와 실제 메뉴·하위 경로를 대조해 전체 목록을 점검한다. 대시보드, 시장 탐색, 관심종목, 트레이딩, 주문·체결, 포트폴리오, 전략 스튜디오, 백테스트, 위험관리, 매매일지, 알림·이벤트, 데이터 상태, 연결·설정, 설계실, KIS 모의 매매와 별도 매매 설정(목차·일반 주문/위험·다음 한정 실행·다음 전략 계약 및 단계)을 포함한다. 지난 KIS 기록은 회귀 기준으로 삼고 DEMO와 현재 KIS도 각각 확인한다.
- #149와 페이지별 기존 기록을 재사용해 보드에 사용자 행동, 관측된 불편, 의존성, 소유 세션, PR, 검증과 사용자 수용 상태를 연결한다. 사용자 영향과 실측 근거로 우선순위를 정한다.
- 수정 작업마다 메인이 독립 Codex 작업 세션·worktree·브랜치를 배정한다. 현재 설치된 orca-cli·orchestration 스킬과 세션 전용 CLI 지침을 따른다. 새 worker에 ‘페이지/경로, 사용자 행동, 기준 SHA, 이슈·필수 자료, 소유 파일, 허용 범위, 완료 조건, 보고 대상’을 전달한다. dispatch ID·실제 세션·경로·첫 응답을 확인하고 ‘진행 중’으로 표시한다. 시작 응답이 불명확하면 이전 요청 ID와 실제 상태를 대조해 중복 실행을 막는다.
- 독립 작업은 병렬 진행하되 App.tsx·공통 CSS·컴포넌트·API 계약의 수정 소유자는 겹치지 않게 한다. 포트·DB를 작업별로 분리한다. 작업자는 지정 범위의 구현·검증·커밋·푸시·PR과 메인 보고를 맡는다. 메인은 작업 회수·충돌 해결·통합 검증·인수인계를 맡는다.

페이지별 판단과 검증
- 1440×900 PC와 390×844 모바일에서 실제 대표 동선을 직접 살펴보고 변경 전후 캡처와 근거를 남긴다. 목록은 첫 결과와 기준 시각, 설정은 저장 효과·복귀·입력 보존, 차트는 출처·기준 시각 등 화면의 목적에 맞게 측정한다. 4303 관찰은 상태를 변경하지 않는 범위로 제한하고, 설정 저장·장애 재현·주문 관련 버튼의 동작 검사는 격리 포트·격리 DB·예시 데이터·가짜 전송기에서 수행한다.
- Graphify로 화면·코드·API·저장소 연결을 찾아 원문과 대조한다. agy의 지정 모델 gemini-4-neon-high와 근거를 검토해 ‘유지 / 개선 / 상세로 이동 / 제거’를 판단한다. 프로젝트의 외부 리뷰 지침과 설정된 review-llm gemini --comparison 경로를 따른다. 사용자나 모델 의견에 문제가 있으면 이유와 대안을 제시한다. 유지가 타당한 화면은 근거를 기록한다.
- 채택한 변경 후 같은 사용자 행동으로 재검증한다. 해당되는 로딩·빈 상태·오류·이전값·미확인·부분 실패, 키보드·모바일, 새로고침·뒤로가기 및 화면 간 종목·환경·입력값 전달을 확인한다. 구현 경계에서 지정 Neon 검토를 받고 중요한 지적은 수정·재검증한다. 지정 모델 실패는 실패로 남기고 임의 대체하지 않는다.
- 결과는 ‘원래 문제 → 결정과 이유 → 달라진 동작 → PC·모바일·키보드·주요 상태별 실측과 미검증 → PR’로 보고한다. 비밀값·계좌 식별자·실제 주문번호는 외부 모델·공개 기록·캡처에서 제외한다.

통합과 종료
- 메인은 PR·CI·리뷰와 실제 checkout을 대조하고 격리 통합 후보에서 화면 사이 동작을 검증한다. Archify 지도에는 바뀐 화면·버튼·결과·이슈를 연결한다. docs/STATE.md는 짧은 재개 목차로, 상세 근거는 작업 문서와 GitHub로 관리한다.
- 이 명령 호출은 main 병합이나 4303 교체 승인이 아니다. main 병합은 사용자가 지정한 PR 묶음에 한해 진행하고 main CI를 확인한다. 4303에는 사용자가 해당 버전의 반영을 승인한 뒤 메인이 적용하고 브라우저에서 검증한다. 실제 KIS 주문·정정·취소·전략 기동·예약, 원장 초기화와 백업 삭제는 승인 범위 밖이다. 기술 검증·병합·실사용 반영·사용자 직접 수용을 따로 기록한다.
- 첫 보고에는 현재 소유·진행 상태, 다음 우선순위와 이유를 짧게 적는다. 배정 가능 작업이 있으면 메인이 직접 시작·회수하고, 대기만 남으면 사용자에게 검토 링크와 결정사항을 제시한다. 모든 화면에 변경 결과 또는 유지 근거, 미검증 범위와 수용 상태가 있는지 확인한다.
