목표
사용자가 각 화면에서 “여기는 무엇을 하는 곳인가, 무엇을 근거로 판단하는가, 이 버튼을 누르면 무엇이 바뀌는가”를 이해하고, 바꾸고 싶은 지점을 가리킬 수 있게 하라. 지난 주문 화면에서 사용한 실측 → Gemini Neon과 판단 → 구현 → 실제 웹 재검증 방식을 나머지 전체 화면에 적용하라. 각 페이지의 핵심 질문과 완료 기준은 그 페이지의 용도에 맞춰 정하라.

1. 중복 배정부터 방지하고 범위와 순서를 정한다
- #149, 페이지 이슈·열린 PR과 Orca의 실제 coordinator/Run/Task/dispatch 상태를 대조하라. 다른 메인이 활동 중이면 그 메인과 확인된 작업 링크를 알려주고 새 Run·worker나 소유권 이전을 시작하지 마라. 상태를 판별할 수 없으면 읽기 전용 확인 결과를 보고하라.
- 기존 작업이 검토·병합·사용자 수용 대기뿐이면 해당 화면·PR·대기 결정을 보고하고 기다려라. 같은 작업을 다시 배정하지 마라. 오래된 기록이나 조용한 터미널만으로 종료 또는 재배정 가능하다고 단정하지 마라.
- AGENTS.md, docs/STATE.md, docs/WORKFLOW.md, 기준 사례와 관련 GitHub 이슈·PR을 먼저 확인하라. 현재 main과 실제 4303을 제공하는 checkout을 대조하고 기존 작업을 이어가라.
- src/App.tsx의 라우트, src/specs.ts, 실제 메뉴·하위 화면을 대조해 빠진 항목 없는 목록을 만들어라. 시작 기준은 대시보드, 시장 탐색, 관심종목, 트레이딩, 주문·체결, 포트폴리오, 전략 스튜디오, 백테스트, 위험관리, 매매일지, 알림·이벤트, 데이터 상태, 연결·설정, 설계실, KIS 모의 매매다. 별도 매매 설정의 목차·일반 주문·위험·다음 한정 실행·다음 전략 계약과 주요 단계도 포함하라.
- 이미 개선한 ‘지난 KIS 실행 기록’은 회귀 검증 기준으로 삼고, 같은 주문·체결 메뉴의 DEMO와 현재 KIS 보기는 각각 점검하라. 기존 지도 #143과 PR #144의 최신 상태도 확인하라.
- 상위 이슈 #149와 기존 페이지 이슈·PR을 재사용하고 보드에 연결하라. 페이지마다 핵심 사용자 행동, 현재 불편, 선행 작업, 담당 세션, PR, 검증 및 사용자 수용 상태를 추적하라. 첫 작업은 사용자 영향, 관측된 불편, 다른 페이지와의 의존성으로 정하고 이유를 한 줄 남겨라.

2. 수정 작업마다 새 세션을 열고 메인이 통제한다
- 메인이 직접 별도 작업 세션·worktree·브랜치를 만들고 지시한 뒤 첫 응답을 확인하라. Orca 환경이면 설치된 orchestration과 orca-cli의 현재 실행 지침을 사용하라. 실제 세션 ID, 작업 경로, 담당 이슈가 맞는지 확인한 뒤 보드를 ‘진행 중’으로 바꿔라.
- 작업자에게 전달할 항목은 ‘담당 화면과 경로 / 사용자 행동 / 기준 커밋 / 이슈와 필수 자료 / 수정 소유 파일 / 검증 조건 / 허용 범위 / 결과를 돌려줄 메인’이다. 작업자는 담당 범위에서 구현·커밋·푸시·PR까지 하고 결과를 메인에 반환한다. 병합·실행 중 앱 반영·다른 작업 배정은 메인이 맡는다.
- 독립 작업은 병렬로 진행하라. App.tsx, 공통 CSS·컴포넌트, API 계약처럼 여러 페이지가 공유하는 변경은 소유자를 한 명 정하거나 순차 통합하라. 테스트 포트·DB는 작업자별로 분리하고, 여러 작업자가 4303을 동시에 바꾸지 않게 하라. 실패·중단된 세션은 마지막 커밋과 소유권을 확인한 뒤 재개하라.

3. 각 작업 세션은 같은 판단 절차를 따른다
- 실제 화면에서 사용자의 대표 작업을 직접 수행하라. PC 1440×900과 모바일 390×844에서 변경 전 캡처와 재현 결과를 남겨라. 목록은 첫 결과·확인 시각, 설정은 저장 효과·복귀·실패 시 입력 보존, 차트는 데이터 출처·기준 시각처럼 해당 화면에서 의미 있는 것을 측정하라.
- Graphify로 관련 화면·컴포넌트·API·저장소 영향을 찾고 원문과 대조하라. 실제 관찰과 제안을 구분해 Gemini 4 Neon High와 ‘유지 / 개선 / 상세로 이동 / 제거’를 결정하라. 다른 의견이 나오면 사용자 과업과 근거로 메인이 판단하라. 내 제안도 불합리하면 이유와 대안을 말하라. 필요한 경우 그대로 유지한다는 결정도 근거와 함께 인정한다.
- 채택한 내용을 구현하고 같은 시나리오로 전후를 비교하라. 정상뿐 아니라 해당되는 로딩·빈 결과·오류·이전값·미확인·부분 실패, 키보드·모바일 동작을 확인하라. 완료 경계에서 지정 Gemini Neon으로 변경분을 검토하고 중요한 지적은 수정·재검증하라. 모델 호출 실패나 대체 모델을 Neon 통과로 기록하지 마라.
- 페이지 결과는 ‘원래 문제 → 결정과 이유 → 바뀐 행동 → 전후 근거 → 남은 한계 → PR’로 짧게 보고하라. 비밀값·계좌 식별자·실제 주문번호는 외부 모델이나 공개 캡처에 넣지 마라.

4. 메인이 통합·검증·인수인계를 책임진다
- PR의 담당 범위, CI, 리뷰, 공통 파일 충돌을 확인하고 묶음별로 통합 검증하라. 페이지 사이에서 종목·환경·입력값·뒤로가기가 이어지는지도 직접 확인하라. 민감 동작은 격리된 예시 데이터로 검증하고 일반 화면 조회는 필요한 읽기 범위에서 수행하라. 실제 KIS 주문·정정·취소·전략 기동·예약, 원장 초기화·백업 삭제는 이 지시의 승인 범위 밖이다.
- 통합 후보는 격리된 예시 앱에서 확인하고 주소와 serving checkout을 기록하라. 4303 반영은 해당 범위에 대한 사용자의 지시를 확인한 메인이 수행하고 실제 브라우저에서 재검증하라. 묶음마다 화면 링크, 바뀐 점, 전후 근거, 남은 결정을 보고하라. Archify 지도에는 변경된 화면·버튼·결과와 해당 이슈를 연결해 사용자가 그 자리에서 다음 수정 의견을 줄 수 있게 하라.
- main 병합은 메인이 검증된 PR 묶음을 제시하고 내가 “병합해”라고 지시한 범위에서 수행하라. 병합 대기 중에도 독립 작업은 계속하라. 병합 뒤 main CI와 실행 checkout을 확인하라. 기술 검증·병합·사용자 직접 수용은 각각 기록하라.
- docs/STATE.md는 짧은 재개 목차로 유지하고 상세 판단은 작업 문서와 GitHub에 남겨라. 마지막에는 모든 페이지에 구현 결과 또는 유지 근거가 있는지, 주요 페이지 간 흐름을 실제로 검증했는지, 남은 미검증·수용 대기가 무엇인지 대조하라.

명령을 호출하면 먼저 현재 상태와 다음 행동을 짧게 보고하라. 배정 가능하고 소유자가 없는 작업이 확인됐을 때만 해당 작업의 새 세션을 실제로 열어 착수 응답까지 확인하라. 이후 메인이 결과 회수와 다음 배정을 이어가라. 승인이나 사용자 수용만 남으면 검토 링크와 결정할 항목을 전달하라.
