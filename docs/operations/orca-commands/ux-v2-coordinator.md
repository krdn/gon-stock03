# Orca ‘2차 UI/UX 업그레이드 총괄’ 제작 기록과 업그레이드 방법

다음 버전을 만들 때는 [등록 본문](ux-v2-coordinator.txt)을 복사해 수정한다. 이 가이드는 **어떤 사용자 문제에서 시작했는지, 무엇을 왜 고쳤는지, 검토한 글과 실제 Orca 설정이 같은지**를 확인하는 데 쓴다. Git에 본문을 저장하는 일과 Orca 호스트의 Quick Command에 반영하는 일은 각각 검증한다.

## 1. 출발점 — 코드를 몰라도 수정할 곳을 가리킬 수 있게

1차에서 사용자가 겪은 어려움은 개발된 화면의 전체 구조와 버튼의 효과를 이해하기 어렵고, 따라서 어떤 변경을 요청할지도 막막하다는 것이었다. Graphify로 화면·코드·API·저장소 연결을 확인하고, Archify 지도에서 실제 캡처와 질문할 위치를 함께 보는 방식을 도입했다. 첫 사례는 주문·체결이었다. 현재 원장만 보여 과거 실행을 찾기 어려운 문제를 먼저 고쳤고, 다음에는 모바일에서 첫 주문과 KIS 확인 시각을 스크롤 없이 읽도록 바꿨다. [화면 지도와 사용자 피드백 #143](https://github.com/krdn/gon-stock03/issues/143) · [원장 PR #146](https://github.com/krdn/gon-stock03/pull/146) · [UI/UX 검토와 측정 #147](https://github.com/krdn/gon-stock03/issues/147) · [화면 변경 PR #148](https://github.com/krdn/gon-stock03/pull/148)

사용자는 이 방식을 나머지 화면에도 적용하되, 작업할 때마다 세션을 직접 열고 설명을 반복하는 일을 메인에게 맡기고 싶어 했다. 그래서 메인은 우선순위·배정·충돌·통합·인수인계를 맡고, 각 작업자는 별도 worktree와 세션에서 자기 화면의 실측·구현·검증·PR을 맡는 프롬프트를 작성했다.

**터미널 셸 명령 대신 Codex Agent Prompt를 선택한 이유**는 첫 행동에 판단이 필요하기 때문이다. 같은 버튼을 눌러도 새 작업이 남았을 때는 작업자를 배정하고, 통합 후보가 이미 마련됐을 때는 검토 링크와 남은 결정을 보여줘야 한다. 등록 준비 시점인 2026년 11월 21일에는 상위 이슈 #149와 통합 초안 PR #187에 16개 화면과 제품 PR 18개의 검토 기록이 있었다. 따라서 최초 프롬프트의 “첫 작업자를 지금 시작”을 그대로 저장하면 중복 작업을 만들 수 있었다. [전체 진행 #149](https://github.com/krdn/gon-stock03/issues/149) · [통합 후보 #187](https://github.com/krdn/gon-stock03/pull/187) · [세션·수용 기록 #153](https://github.com/krdn/gon-stock03/pull/153)

Neon 호출의 초기화 모델은 `gemini-4-neon-high`, 최종 이벤트는 `SUCCESS`였다. 이는 지적 사항이 담긴 **리뷰 응답을 받았다**는 뜻이다. Opus 1차 판정은 **수정 필요**, 수정 후 같은 본문에 대한 최종 판정은 **PASS**였다. 두 Opus 응답의 `modelUsage`에 `claude-opus-5-5`가 있었고 요청 강도는 high였다. 공급자 내부 처리 강도는 별도로 확인하지 않았다. 이 두 모델은 명령 제작의 검토자이고, 등록된 명령을 수행하는 에이전트는 Codex다. 페이지마다 Opus 재리뷰를 추가하라는 운영 규칙으로 확대하지 않는다.

## 3. Orca에 무엇을 어떻게 저장했나

| 필드 | 등록값 |
| --- | --- |
| 표시 이름 | `2차 UI/UX 업그레이드 총괄` |
| 고정 명령 ID | `gon-stock03-ux-v2-coordinator` |
| Action / Agent | `Agent Prompt` (`agent-prompt`) / `Codex` (`codex`) |
| Scope | Project · `gon-stock03`. 내부 형식은 `{ type: "repo", repoId: <이 호스트의 프로젝트 ID> }` |
| 등록 본문 | [편집용 UTF-8 파일](ux-v2-coordinator.txt) · 7,472바이트 · 마지막 개행 없음 |
| 기준 SHA-256 | `c3f1f207d0cd35acc6ce82aefacee4de59fffe73b3949a9bbb9b5763aba12fc5` |

Orca 1.4.265의 프로젝트 설정에 저장했다. 일반 UI 경로는 **Settings → Quick Commands**다. 이 PC에서는 GNOME Wayland 창의 설정 컨트롤을 접근성 트리에서 확인하지 못해, 설치된 동일 버전 Orca의 설정 클라이언트를 이용했다. 설정 DB를 직접 편집하지 않았다. 호스트별 저장 위치와 Global/Project 범위는 별개이므로 다른 PC에서 등록할 때는 그 호스트에서 프로젝트를 다시 찾는다. [Orca 공식 설정 안내](https://orca.dev/docs/settings#quick-commands)

실제 등록 순서는 다음과 같았다.

1. 세션 지정 CLI의 `repo show --repo path:<기본 checkout> --json`으로 저장소 경로와 Orca 프로젝트 ID를 확인했다. 기존 목록에서 같은 명령 ID와 같은 프로젝트의 동명 명령을 검사했다.
2. 최종 본문을 설치 버전의 명령 스키마로 검사했다. `settings.updateTerminalQuickCommands`에 단일 `upsert`를 보내 기존 목록 중 대상 한 건만 저장했다. 이 이름들은 해당 버전의 **설정 API 메서드**다. 셸의 Orca 서브커맨드로 입력하는 이름이 아니다.
3. 새 클라이언트에서 `settings.getTerminalQuickCommands`로 재조회했다. ID가 정확히 한 건인지, 유형·에이전트·프로젝트 범위가 맞는지, 본문의 UTF-8 바이트가 Opus 최종 검토 입력과 같은지 확인했다. 설치 버전의 범위 판정기로 다른 저장소에 해당 명령이 매칭되지 않는 것도 검사했다.
4. 등록 당시 전체 명령 수는 8개에서 9개가 됐고 기존 8개 항목은 그대로였다. 문서화 때도 설정을 **다시 읽어** 위 해시와 일치하는 원문을 이 저장소에 옮겼다. 등록과 읽기 검증까지 관측했고, 이 검증을 위해 명령을 눌러 신규 팀을 시작한 적은 없다.

## 4. 다음 버전 만들기

**① 현재값 보존.** 해당 호스트의 Quick Commands에서 프로젝트, 에이전트, 명령 ID를 확인하고 본문을 별도 파일에 내보낸다. 저장소 파일의 해시와 다르면 그 차이부터 검토한다. 파일 끝 개행이나 CRLF 변환도 해시를 바꾼다. 이전 등록본의 커밋과 해시는 복구 기준으로 남긴다.

```sh
sha256sum docs/operations/orca-commands/ux-v2-coordinator.txt
git log --oneline -- docs/operations/orca-commands/ux-v2-coordinator.txt
```

**② 변경 제안.** 전용 이슈·브랜치에서 [본문](ux-v2-coordinator.txt)을 수정한다. PR에 “어떤 상황에서 기존 명령이 어떤 잘못된 행동을 할 수 있는지 → 새 판단 → 확인 방법”을 적는다. 이슈 번호나 포트를 바꿀 때는 실제 활성 작업·실행 checkout과 대조한다. 등록 시점의 16개 화면·18개 PR은 당시 근거다.

**③ 두 모델에 순서대로 검토 요청.** 먼저 Neon에 이전본과 후보의 차이, 대표 반례, 호출·배정·승인 범위를 준다. 지적별 채택·기각 이유를 남긴다. 반영한 후보 **전문**과 변경 이유를 Opus에 넘긴다. 수정 요구가 있으면 고친 전문으로 재검토한다. 실행기에 넣을 리뷰 자료에는 비밀값, 계좌 식별자, 실제 주문번호를 포함하지 않는다.

```sh
~/.codex/bin/review-llm gemini --comparison --dry-run
~/.codex/bin/review-llm gemini --comparison < neon-review-input.txt
~/.codex/bin/review-llm --dry-run
~/.codex/bin/review-llm < opus-review-input.txt
```

위 입력 파일은 업그레이드마다 준비하는 리뷰 자료다. dry-run 출력에서 Neon은 `agy / gemini-4-neon-high`, Opus는 `claude-opus-5-5 / high`인지 확인한다. 출력의 호출 성공 여부와 본문 판정을 모두 읽는다. 최종 PASS를 받은 원문의 해시를 기록한다.

**④ 같은 ID로 갱신.** 대상 프로젝트에서 기존 항목을 편집한다. 설정 API를 쓸 때는 현재 설치 버전의 스키마와 프로젝트 ID를 다시 확인하고 같은 ID를 upsert한다. 저장 전후에 별도 조회를 하여 ID 한 건, repo 범위, Codex, 본문 해시, 다른 명령 보존을 검사한다. GitHub에 문서를 올리는 일만으로 이미 설치된 호스트의 명령이 바뀌지는 않는다.

**⑤ 필요할 때만 실행 검증.** 저장 검증은 명령 실행 없이 끝낼 수 있다. 실제 호출을 검증할 때는 아래 상황과 기대 행동을 기록한다. 수정 세션을 배정하거나 운영 작업을 시험할 권한은 해당 요청의 범위에서 확인한다.

| 상황 | 기대 행동 |
| --- | --- |
| 다른 활성 메인이 있거나 소유권 조회가 불완전함 | 확인한 위치·불확실한 점을 보고. 중복 Run·worker 생성 0건 |
| 모든 페이지가 검토·승인 대기 또는 완료 | 기존 화면·PR 링크와 사용자 결정사항 안내. 재배정 0건 |
| 일부 PR은 대기 중이고 독립 미배정 작업이 있음 | 승인 범위와 파일 소유를 확인하고 해당 작업만 배정. dispatch ID·실제 세션·경로·첫 응답 확인 |
| 미배정으로 보이지만 기존 PR과 파일이 겹침 | 선행 통합 또는 명시적 인계를 기다리고 원래 PR head를 보존 |
| 사용자가 검토만 요청함 | 기술 검증·사용자 수용·main 병합·4303 반영을 따로 기록. 모의 포함 KIS 주문 전송 0건 |

**복구.** 문제가 있으면 이전에 재조회로 확인한 Git 커밋의 본문을 같은 Orca 명령 ID에 복원하고 그 버전의 SHA-256으로 재조회한다. 프리셋 복구와 이미 실행 중인 세션의 중지·인계는 별도 작업이다.

## 5. 다음 리뷰에서 먼저 볼 두 가지

Opus는 아래 두 점을 **등록을 막지 않는 개선 후보**로 남겼다. 위 기준 해시의 원문에는 추가하지 않았다.

- 파일 소유권의 “검토 대기 PR”에 **진행 중인 열린 PR과 draft PR**까지 포함한다고 더 명확히 쓸 것인가?
