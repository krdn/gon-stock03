Answer

GON Stock은 국내 주식·ETF를 조회하고 모의 매매를 연구하는 개인 PC용 앱이다. 15개 화면이 로컬 서버 하나를 공유한다. 시세의 출처와 주문을 처리하는 주체를 알면 화면에 표시된 숫자의 의미를 구분할 수 있다.

  1. KIS 시세 화면은 한국투자증권에서 읽은 가격을 보여준다. 모의 주문은 별도 매매 화면에서 요청한다.1
  2. DEMO 주문은 합성 봉을 한 칸 진행하면 로컬 엔진이 체결을 평가한다.2
  3. 저장 일봉 백테스트는 입력과 결과를 하나의 실험으로 남긴다. 같은 실험을 다시 계산해 결과를 비교할 수 있다.3

개발 환경에서 Vite는 4303번 포트로 화면을 제공하고 API 요청을 Node.js 서버의 4304번 포트로 전달한다. React는 3초마다 로컬 상태를 확인한다. WebSocket은 서버에서 연결하고, 수신한 체결가와 주문 통보를 REST 조회와 대조한다.4 5 6

  • broker → kis · 검사 통과 후 주문

  • broker → ledger · 확인된 상태 저장
  • 접수와 체결은 별도 상태다. 주문·체결 내역을 다시 조회해 체결 수량과 잔량을 갱신한다.7

15개 화면은 어떤 일을 하는가?

화면 주소는 React 라우터에 등록된 경로다. 프로젝트를 실행했을 때 해당 메뉴에서 이용할 수 있다.10 5

화면주소역할과 데이터 출처
대시보드/dashboardDEMO와 KIS의 저장 잔고·미체결·전략 상태를 나누어 요약한다.
시장 탐색/market공식 종목 마스터에서 종목을 찾고 KIS REST 현재가를 조회한다.
관심종목/watchlistSQLite에 보관한 관심목록과 종목별 시세를 확인한다.
트레이딩/trade기본 화면에 KIS 현재가·일봉을 표시한다. DEMO 탭은 합성 시세를 쓴다.
주문·체결/ordersDEMO 주문과 KIS 모의 원장을 각각 조회하고 상태·잔량을 확인한다.
포트폴리오/portfolio환경별 보유·평가를 살피고 KIS 잔고 응답의 완전성을 확인한다.
전략 스튜디오/strategies이동평균 전략을 설정하고 환경별 신호와 실행·정지 이유를 확인한다.
백테스트/backtest저장 일봉 실험을 실행·재현하거나 DEMO 입력으로 계산한다.
위험관리/risk주문·종목·손실 한도와 신규 주문 긴급정지를 관리한다.
매매일지/journal종목별 메모를 저장하고 작성한 내용을 검색한다.
알림·이벤트/alertsDEMO 이벤트와 KIS 감사 기록에서 주문·연결 상태 변화를 추적한다.
데이터 상태/data마스터와 일봉의 출처·기간·누락·수집 상태를 확인한다.
연결·설정/settings실행 환경을 점검하고 KIS 모의 인증 및 잔고 조회 결과를 확인한다.
설계실/design화면별 목적, API 설계, 구현 근거와 후속 작업을 읽는다.
KIS 모의 매매/paper모의 계좌를 조회하고 주문 요청·결과 대조·불명 주문 복구를 진행한다.

종목 마스터·일봉·백테스트는 어떻게 이어지는가?

Diagram structure
  • 수집 조건 선택 select
  • 일봉 구간 수집 collect
  • 달력·봉 품질 확인 check
  • 전략 성과 계산 calc
  • 실험 스냅샷 저장 save
  • 고정 입력 재현 replay
  • calc → save · 입력·결과
  • check → calc · 통과
  • collect → check · 일자별 봉
  • save → replay · 같은 실험
  • select → collect · 종목·기간

공개 마스터는 종목 검색용 목록이다. 백테스트에는 별도로 모은 KIS 일봉을 쓴다. 종목·기간·수정주가 정책을 고정하고, 거래일 누락·중복이 있거나 수집이 덜 된 입력은 거부한다.11 3

이동평균 교차는 종가로 판정하고 다음 봉의 시가에 슬리피지와 수수료를 반영한다. 매일 현금과 보유분의 종가 평가액을 합쳐 수익률과 최대 낙폭을 계산한다. 입력 봉·설정·엔진 버전·해시가 결과와 함께 저장된다.2 3

SQLite에는 무엇이 남는가?

저장 단위테이블읽는 기능과 쓰는 시점
워크스페이스workspaceDEMO 주문·보유, 관심목록, 일지, 위험 설정 등 공통 상태의 변경을 저장한다.
모의 주문paper_orders, paper_audit, paper_event_read요청 ID로 주문 상태와 감사 이력을 조회한다. 알림을 읽었는지도 별도로 남긴다.
위험·승인paper_baseline, paper_run, paper_cancel_attempt일별 평가 기준과 제한된 실행·취소 시도를 기록한다.
실시간·전략realtime_guard, strategy_contract, strategy_claim재시작과 중복 신호를 처리하고 계약별 전송 시도·금액을 보존한다.
종목과 가격market_master, market_instruments, market_removed, daily_runs, daily_bars시장별 마스터와 구성 변화를 저장한다. 개별 수집의 봉은 수집 ID와 거래일로 구별한다.
백테스트backtest_experiments고정 입력과 계산 결과를 보존해 이후 원본 수집 자료가 바뀌어도 재현할 수 있다.

기본 저장소는 로컬 SQLite이며 WAL 모드를 사용한다. 일반 앱, 전략 계약용 원장, 독립 모의 테스트 실행기의 기록은 쓰임이 다르다. 실행기의 기록은 분리되지만 같은 증권사 모의 계좌를 사용하면 보유·미체결은 공유된다.12 13 14

코드를 바꾸려면 어느 파일부터 보는가?

위치담당하는 코드먼저 볼 지점
src/진입점·라우팅·공통 상태main.tsx에서 앱을 시작한다. App.tsx는 상태를 새로 읽고 context.tsx를 통해 화면에 전달한다.5
src/pages/시세·연구·운영 화면LiveTrading.tsx는 실제 시세, Paper.tsx는 모의 주문, Research.tsx는 전략·백테스트 화면을 담당한다.1 10
src/components/공유 화면 요소ui.tsx는 표·패널·상태 표시, RealtimeStatus.tsx는 실시간 연결과 대조 상태를 보여준다.15
shared/프런트와 서버의 공통 계약model.ts의 상태 타입, contracts.ts의 Zod 검사, status.ts의 시각·신선도 규칙을 함께 쓴다.16
server/HTTP 진입점과 업무 로직http.ts가 요청을 나눈다. kis.ts는 REST, paper.ts는 모의 주문, realtime.ts는 구독·전략 신호, events.ts는 운영 이벤트를 맡는다.17
scripts/실행과 점검dev.ts는 개발 서버와 화면을 시작한다. vts-runner.ts는 지정된 모의 주문을 별도 원장에서 확인하는 실행기다.18 14
tests/ · .github/workflows/회귀 검증Node 테스트로 계산·계약·저장을 검증한다. Playwright는 실제 브라우저에서 화면 전환과 오류 처리를 검사한다.19
docs/설계·작업·검증 근거STATE.md는 현재 작업을 안내한다. tasks/는 완료 기준, verification/은 실행 결과, operations/는 운영 절차를 담는다.20
.project-map/ · public/ · graphify-out/프로젝트를 탐색하는 자료개발 과정 지도는 목표부터 KIS 연동까지의 이력을 보여준다. Graphify 결과는 파일·심벌 사이 관계를 찾는 데 쓴다.21 22

문제가 생기면 어디서 확인하는가?

상황먼저 확인할 곳판별 기준
화면의 가격·잔고가 오래됨연결·설정, 데이터 상태마지막 성공 시각과 응답 완전성을 확인한다. 로컬 서버 상태와 KIS 잔고 상태는 따로 판정한다.23
실시간 신호가 생겼으나 주문이 없음전략 스튜디오, KIS 원장구독 승인·REST 대조·신호 시각·사전검사 지연·계약 잔여 한도를 본다. 신호와 증권사 접수는 별개 사건이다.24
주문 응답이 끊김KIS 모의 매매, 주문 감사 이력같은 요청 ID로 원장과 증권사 주문 내역을 대조한다. 모바일 확인을 거친 복구 사례가 있다.8
백테스트 숫자를 재검증하고 싶음백테스트, 데이터 상태수집 ID·수정주가 정책·거래일과 실험 해시를 확인하고 저장된 스냅샷으로 재계산한다.3
